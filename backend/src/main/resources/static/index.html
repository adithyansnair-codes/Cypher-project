DESIGN

                
Algorithms

                
How one frame becomes a prioritised, acknowledged incident.

            


            

        


        


            

                
Weapon detection — YOLOv8n, fine-tuned

                ai/app/detector.py
                

                    Single-shot detection: one forward pass over a 416 px frame returns
                    boxes, classes and confidences together. No region proposals, which is why
                    it keeps up with a live feed.
                

                
    
                    
  • Classes: knife, pistol — 4,409 train / 1,043 val images
    • 
                    
  • Validation: mAP@50 0.589, mAP@50-95 0.403
    • 
                    
  • 416 px input chosen for latency, not accuracy
    • 
                

            


            

                
False-positive suppression — three rules

                ai/app/main.py
                
The part that needed measuring rather than guessing.

                
    
                    
  • One incident per object class per frame — a single photo returned five identical boxes
    • 
                    
  • 8-frame confirmation streak (~⅓ s at 27 fps): a webcam run scored “pistol” on 1,282 frames at 35–55 % with no pistol present, so one frame is not evidence
    • 
                    
  • 90 s cooldown per class per camera, or a 30 fps stream raises 30 incidents a second
    • 
                

            


            

                
Severity grading — decided by the gateway

                IncidentService.deriveSeverity
                

                    The detector reports what it saw; the gateway decides how serious it is, so a
                    new model cannot invent its own priority vocabulary.
                

                
    
                    
  • weapon · knife · pistol · rifle · gun · fire → CRITICAL, whatever the confidence
    • 
                    
  • smoke · fall → HIGH at ≥ 85 %, otherwise MEDIUM
    • 
                    
  • everything else by confidence: ≥ 90 HIGH, ≥ 70 MEDIUM, else LOW
    • 
                

            


            

                
Atomic ingest — incident and alert in one transaction

                create_incident_with_alert()
                

                    The AI engine posts a detection; a stored procedure writes the incident and
                    its alert together, and a trigger closes the alert when the incident is
                    resolved. Detection → incident → alert cannot half-happen.
                

            


            

                
Authentication — BCrypt + HS256 JWT

                JwtService · JwtAuthenticationFilter
                
    
                    
  • Passwords stored as BCrypt hashes (cost 10), never plaintext
    • 
                    
  • The token carries the role; a stateless filter verifies signature and expiry on every request
    • 
                    
  • The WebSocket handshake carries the same token, because a browser cannot set headers on it
    • 
                

            


            

                
Live delivery — pushed after commit

                IncidentSocketHandler
                

                    Events broadcast to every open cockpit, but only once the transaction has
                    committed, so a rolled-back change is never announced. The client reconnects
                    with backoff and falls back to polling if the channel stays down.
                

            


            

                
Authorisation and audit — enforced and recorded

                SecurityConfig · trg_incident_changes
                

                    Roles are checked server-side against the matrix the seeded
                    role_permissions rows describe, and every incident change is
                    written to audit_logs by a trigger — the trail exists whatever
                    made the change.
                

            


            

                
Reporting — three formats, one surface

                reporting/ (C#)
                

                    CSV, Excel and PDF rendered by the reporting worker straight from PostgreSQL;
                    the gateway proxies them so the cockpit keeps one origin and one token, and
                    the worker stays on the loopback interface.
